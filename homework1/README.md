# Kafka: продюсер и два консьюмера

Учебное приложение на Python (`confluent-kafka`): продюсер отправляет JSON-сообщения
в топик `my-topic`, два консьюмера независимо читают их — по одному и пачками.
Формат значения проверяется по JSON Schema из Schema Registry.

## Инфраструктура (`docker-compose.yaml`)

| Сервис            | Порт на хосте  | Назначение                                |
|-------------------|----------------|-------------------------------------------|
| zookeeper         | 2181           | координация кластера                      |
| kafka-0/1/2       | 9092/9096/9095 | три брокера, репликация по умолчанию = 3  |
| schema-registry   | 8081           | хранение JSON-схемы сообщений             |
| kafka-ui          | 8080           | веб-интерфейс для просмотра топиков/групп |
| app               | —              | приложение из `main.py`, 2 реплики (`deploy.replicas: 2`) |

## Классы (`main.py`)

- **`MessageProducer`** — `SerializingProducer` с `enable.idempotence=true` (без дублей при ретраях),
  `retries`, `retry.backoff.ms` и `delivery.timeout.ms`. Ключ сериализуется как строка,
  значение `{"id": <uuid>, "text": ...}` — как JSON по схеме. Раз в 3 секунды вызывает `send()`,
  результат доставки логируется в `_delivery_report` (топик, партиция).
- **`SingleMessageConsumer`** — читает сообщения по одному через `poll()`,
  `enable.auto.commit=true`: offset фиксируется автоматически. Группа `single-group`.
- **`BatchMessageConsumer`** — забирает сообщения через `consume()`, складывает в буфер и,
  когда набралось `batch_size` (10), логирует пачку и вручную коммитит offset
  (`enable.auto.commit=false`, коммит только после обработки — at-least-once).
  Ждёт накопления `fetch.min.bytes` (до `fetch.wait.max.ms`). Группа `batch-group`.

Все три класса запускаются в отдельных потоках; `Ctrl+C` останавливает их корректно.
Консьюмеры в разных группах, поэтому каждый получает **все** сообщения топика.

Ошибки доставки и десериализации пишутся в лог, потоки продолжают работать.

### Две реплики приложения

Сервис `app` запускается в двух экземплярах. Каждый экземпляр содержит свой продюсер и
оба консьюмера, поэтому в топик пишут оба (ключи `key-N` в них совпадают). Консьюмеры одной группы
(`single-group` / `batch-group`) делят между репликами партиции топика (3 партиции на 2 реплики):
каждое сообщение обрабатывает только одна реплика каждой группы, а сами группы
по-прежнему получают весь поток независимо друг от друга.

Адреса брокеров и Schema Registry передаются через переменные окружения
`BOOTSTRAP_SERVERS` и `SCHEMA_REGISTRY_URL` (в compose заданы внутренние адреса docker-сети).

## Запуск

```bash
# 1. Поднять кластер (без приложения: оно запустится после создания топика)
docker compose up -d zookeeper kafka-0 kafka-1 kafka-2 schema-registry kafka-ui

# 2. Создать топик с 3 партициями и 2 репликами (команда и результат describe — в topic.txt)
docker compose exec kafka-0 kafka-topics --create --topic my-topic \
  --bootstrap-server kafka-0:29092 --partitions 3 --replication-factor 2

# 3. Запустить две реплики приложения
docker compose up -d --build app

# 4. Смотреть логи
docker compose logs -f app
```

## Как проверить, что всё работает

0. `docker compose ps app` показывает два запущенных контейнера (`kafka-app-1`, `kafka-app-2`).
1. В логах (`docker compose logs -f app`) каждые ~3 секунды появляется
   `Сообщение доставлено [key=key-N, value=..., topic=my-topic, partition=...]` — продюсер работает.
2. Сразу следом `SingleMessageConsumer` пишет `Получено сообщение: key=..., value=...` —
   одиночное чтение.
3. Примерно раз в 30 секунд (10 сообщений) `BatchMessageConsumer` пишет
   `Получена пачка из 10 сообщений: ...` — пакетное чтение с ручным коммитом.
4. В Kafka UI (<http://localhost:8080>) → Topics → `my-topic` видны 3 партиции с 2 репликами,
   в Consumers — группы `single-group` и `batch-group`, в каждой по 2 участника
   (партиции распределены между репликами).
5. В Schema Registry зарегистрирована схема: `curl http://localhost:8081/subjects`
   (должен быть subject `my-topic-value`).
6. Отказоустойчивость: `docker compose stop kafka-2` — приложение продолжает
   работать на оставшихся брокерах.
